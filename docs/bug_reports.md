## Окружение и обозначения

- Ручной запуск: локальный бэкенд, PostgreSQL,адрес `http://127.0.0.1:8000`
- Во всех POST-запросах используется `Content-Type: application/json`.
- `{{vk_secret}}` — фактический непустой `VK_SECRET_KEY`; `{{vk_user_id}}` — числовой VK ID тестового сотрудника; `{{shift_id}}` — ID подготовленной смены.

## BUG-01. История откликов доступна без авторизации

**Компонент:** `GET /api/shift-responses`, функция `get_shift_responses()`  
**Серьёзность:** Высокая  
**Приоритет:** Высокий  

### Предусловия

Бэкенд и PostgreSQL запущены. В `shift_responses` есть хотя бы один отклик сотрудника.

### Шаги воспроизведения

1. Создать в Postman GET-запрос на `http://127.0.0.1:8000/api/shift-responses`.
2. В Authorization выбрать `No Auth`.
3. Удалить заголовки `Authorization` и `Cookie`, если они присутствуют.
4. Отправить запрос без тела.

### Фактический результат

Сервер возвращает JSON с массивом `responses`, содержащим сведения об откликах: `business_id`, `shift_id`, `vk_id`, `employee_id`, должность, статус и сообщение отклика. Данные доступны без передачи учётных данных.

### Ожидаемый результат

Неаутентифицированный запрос отклоняется, данные сотрудников не возвращаются. После аутентификации история ограничивается организациями, к которым у пользователя есть доступ.



## BUG-02. Отправка сообщений доступна без авторизации

**Компонент:** `POST /api/send-shift-notification`, функция `send_shift_notification()`  
**Серьёзность:** Высокая  
**Приоритет:** Высокий  

### Предусловия

Бэкенд и PostgreSQL запущены. На сервере настроен действующий токен сообщества VK. Тестовый аккаунт разрешил сообщения от сообщества.

### Шаги воспроизведения

1. Создать POST-запрос на `http://127.0.0.1:8000/api/send-shift-notification`.
2. Выбрать `No Auth`, удалить заголовки `Authorization` и `Cookie`.
3. Подставить VK ID своего тестового аккаунта и отправить тело:

```json
{
  "shift_id": null,
  "message": "BUG-02: отправка без авторизации",
  "user_ids": [{{vk_user_id}}],
  "open_positions": []
}
```

4. Просмотреть ответ, диалог с сообществом и записи `sent_notifications` для указанного текста.

### Фактический результат

Неавторизованный запрос допускается к отправке: сервер использует собственный токен сообщества для обращения к VK по переданному `user_id`.

### Ожидаемый результат

Запрос без аутентификации отклоняется до отправки сообщения. Для авторизованного пользователя учитываются права на рассылку и выбранных получателей.


## BUG-03. Невалидные данные callback вызывают HTTP 500

**Компонент:** `POST /vk/callback`, функция `vk_callback()`  
**Серьёзность:** Средняя  
**Приоритет:** Средний  

### Предусловия

Бэкенд запущен. На сервере задан непустой `VK_SECRET_KEY`, его правильное значение сохранено в Postman как `vk_secret`. Создание смены и сотрудников не требуется.

### Шаги воспроизведения

1. Создать POST-запрос на `http://127.0.0.1:8000/vk/callback`.
2. Отправить тело с правильным секретом и `object = null`:

```json
{
  "type": "message_event",
  "secret": "{{vk_secret}}",
  "object": null
}
```

3. Просмотреть HTTP-ответ и traceback в консоли сервера.

### Фактический результат

HTTP 500, тело `Internal Server Error`. В обработчике возникает исключение:

```text
AttributeError: 'NoneType' object has no attribute 'get'
```

Ошибка воспроизведена локальным HTTP-запросом без обращения к БД и VK.

### Ожидаемый результат

Сервер отклоняет некорректную структуру контролируемым ответом об ошибке клиента, например HTTP 400 или 422, с указанием проблемного поля. Необработанное исключение не возникает.

## BUG-04. Пустой секрет отключает защиту callback

**Компонент:** настройка `VK_SECRET_KEY`, функция `vk_callback()`  
**Серьёзность:** Высокая  
**Приоритет:** Высокий  

### Предусловия

Доступны настройки и перезапуск локального бэкенда. Для ручного получения сообщения настроен действующий токен сообщества, тестовый VK-аккаунт разрешил сообщения.

### Шаги воспроизведения

1. Сохранить исходное значение `VK_SECRET_KEY` и остановить сервер.
2. Установить в `.env` пустое значение `VK_SECRET_KEY=`. Удалить одноимённую переменную из окружения запуска, если она задана.
3. Перезапустить сервер.
4. Отправить POST на `http://127.0.0.1:8000/vk/callback` без поля `secret`:

```json
{
  "type": "message_event",
  "object": {
    "user_id": {{vk_user_id}},
    "payload": {
      "type": "my_shifts"
    }
  }
}
```

5. Просмотреть ответ и результат выполнения действия.

### Фактический результат

При пустом ключе запрос без секрета допускается к выполнению действия. В локальном исследовании обработчик вызвал `send_my_shifts()` и вернул HTTP 200 с телом `ok`; отправка списка смен была заменена регистрируемым вызовом.

По коду значение `change_me` также преобразуется в пустой ключ.

### Ожидаемый результат

Отсутствие секрета не должно разрешать выполнение защищённых действий. Сервер явно сообщает об ошибке конфигурации либо отклоняет такие события до выполнения бизнес-операций.

## BUG-05. Ошибка уведомления VK приводит к HTTP 502 после успешного назначения сотрудника

**Компонент:** `POST /vk/callback`, функции `save_shift_response()`, `send_my_shifts()` и `vk_api()`  
**Серьёзность:** Средняя  
**Приоритет:** Средний  


### Предусловия

1. Бэкенд и PostgreSQL запущены, настроены правильные секрет и токен сообщества.
2. Создана будущая смена с одним свободным местом на должность «Продавец».
3. Активный сотрудник этой организации имеет подходящую должность, привязанный VK ID и ещё не назначен на смену.
4. Тестовый сотрудник запретил сообщения сообщества.

### Шаги воспроизведения

1. Зафиксировать исходное состояние: сохранить назначения сотрудника, свободную позицию и историю откликов подготовленной смены.

2. Отправить отклик: отправить POST на `http://127.0.0.1:8000/vk/callback` с правильным секретом:

```json
{
  "type": "message_event",
  "secret": "{{vk_secret}}",
  "object": {
    "user_id": {{vk_user_id}},
    "payload": {
      "type": "shift_response",
      "shift_id": {{shift_id}},
      "position": "Продавец"
    }
  }
}
```

3. Сопоставить HTTP-ответ и состояние операции: просмотреть ответ, `shift_assignments`, `shift_open_positions` и новый отклик в `shift_responses`.

### Фактический результат

При подставном отказе VK в отправке получен HTTP 502 с описанием запрета сообщений. До ошибки выполнены операции создания назначения и отклика, а контекст транзакции завершён без исключения. 

Последовательность кода подтверждает причину: `save_shift_response()` завершает свою транзакцию до вызова `send_my_shifts()`. Следовательно, ошибка доставки возникает уже после успешной бизнес-операции и не откатывает её.

### Ожидаемый результат

Сбой уведомления отделяется от результата записи на смену: успешное назначение сохраняется, ошибка доставки регистрируется отдельно, а callback получает подтверждение обработанного события.

## Расхождения валидации, выявленные автотестами

При запуске Python-набора получено 16 passed и 4 failed. Ошибки оставлены для
демонстрации найденных расхождений. Точные коды 404/422 — принятый тестовый контракт,
в задании они не определены для каждого случая отдельно.

Уведомление с несуществующим shift_id: ожидается 404 без отправки сообщения и записи
уведомления. Фактически возвращается 200 со статусом sent, вызывается мок VK и
создаётся запись sent_notifications.

Уведомление с user_ids=[-1]: ожидается 422 без отправки и записи уведомления.
Фактически возвращается 200 со статусом sent, вызывается мок VK и создаётся запись
с отрицательным ID получателя.

Уведомление с open_positions=[]: ожидается 422 без отправки и записи уведомления.
Фактически возвращается 200 со статусом sent, вызывается мок VK и создаётся запись
sent_notifications.

Callback с object.user_id=-1: ожидается 422 без обработки отклика. Фактически
возвращается 200 с текстом ok, сохраняется отклик rejected и запись журнала,
вызывается мок VK. Назначение не создаётся, число мест не уменьшается.

Настоящая доставка сообщений не проверяется: исходящий VK API подменён моком.
Сценарии воспроизводятся в backend_tests/test_api.py. Запуск из корня проекта:
backend\.venv\Scripts\python.exe -m pytest backend_tests/test_api.py -v
